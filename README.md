# DocsRAG

Grounded question answering over your own documents — with citations, hybrid
**vector + graph** retrieval, and a real evaluation harness.

Ask a question, get an answer that is built only from your documents, with the
source passages it used. Built to mirror production RAG work: measured quality,
not a notebook demo.

## Headline results

Quality is measured by the eval harness, not asserted. The numbers below are
regenerated by `make eval` (which writes `evals/results.md`) so they always
reflect the current code and corpus — run it on the included sample corpus, then
point `DATA_DIR` at your own documents and re-run.

| Metric | How it's measured |
|--------|-------------------|
| Context precision@5 | retrieved chunks from a labelled source / total retrieved — no API key |
| Context recall | labelled sources that were retrieved / all labelled — no API key |
| Mean reciprocal rank | rank of the first relevant chunk — no API key |
| Faithfulness | LLM-as-judge: is every claim supported by the retrieved context? |
| Fact coverage | LLM-as-judge: fraction of expected facts stated |
| Abstention accuracy | did the model decline on the 2 unanswerable questions? |
| Latency p50 / p95 | end-to-end per `make eval` run |

```bash
make ingest              # build the index (local embeddings, no API key)
make retrieval-eval      # context precision / recall / MRR — no API key, no cost
make eval                # adds LLM-judged faithfulness (needs a generation key)
```

The retrieval metrics need no API key at all; only the optional faithfulness,
fact-coverage, and abstention scores call a generation model.

##  Architecture

```
                 ┌──────────────┐
   documents ───▶│   ingest     │  chunk (heading-aware) → embed → index
  (md/pdf/txt)   └──────┬───────┘
                        ▼
              ┌───────────────────┐      ┌──────────────────┐
              │  vector store     │      │   chunk graph    │
              │ (cosine, in-mem)  │      │ (shared-term     │
              └─────────┬─────────┘      │  Jaccard edges)  │
                        │                └────────┬─────────┘
        question ──────▶│  top-k  ───────────────▶│ expand neighbours
                        ▼                         ▼
                   ┌──────────────────────────────────┐
                   │  grounded prompt + citations      │──▶ Claude / GPT
                   └──────────────────────────────────┘
                        │
                        ▼
                answer + [n] citations + latency
```

**Why a graph layer?** Plain top-k vector search finds chunks that *look like* the
question but misses chunks that are *related* to a good hit without sharing its
wording — the classic multi-hop miss. DocsRAG builds a lightweight graph linking
chunks that share salient (tf-idf weighted) terms, then expands the vector hits
with their strongest neighbours before generation. It's a public, data-free
version of the graph-retrieval approach I work on professionally.

##  Features

- **Hybrid retrieval** — dense vector search plus graph expansion (toggleable).
- **Citations** — every answer carries the source passages it used.
- **Honest abstention** — says "I don't have that" instead of hallucinating.
- **Provider-agnostic generation** — Anthropic or OpenAI via one env var.
- **Local embeddings** — `sentence-transformers`, no embedding API cost.
- **Evaluation harness** — retrieval metrics + LLM-as-judge faithfulness.
- **FastAPI** backend and a **Streamlit** chat UI; **Docker Compose** for both.

##  Evaluation

Quality is measured, not assumed. `evals/eval_set.jsonl` holds 17 questions —
15 answerable (each labelled with the facts and source files it should rely on)
and 2 deliberately unanswerable, to check the model abstains instead of inventing
an answer.

`make eval` measures:

- **Retrieval** — context precision@k, recall, and MRR against the labelled
  relevant sources (no API key needed).
- **Generation** — an LLM-as-judge scores **faithfulness** (is every claim
  supported by the retrieved context?) and **fact coverage**, plus **abstention
  accuracy** on the unanswerable questions.

Results are written to `evals/results.md` and `evals/results.json`.

## Run locally

Requires **Python 3.11 or 3.12** — the embedding model depends on PyTorch, which
does not yet publish wheels for 3.13+. The bundled `.python-version` selects 3.12
automatically under pyenv; otherwise create the venv with an explicit 3.12
(`python3.12 -m venv .venv`).

```bash
# 1. install
make install                 # or: pip install -r requirements.txt

# 2. build the index over the sample docs (or your own — set DATA_DIR)
make ingest                  # local embeddings, no API key needed

# 3. measure retrieval quality — no API key, no cost
make retrieval-eval

# 4. (optional) add a key for generation and the full eval
cp .env.example .env         # then set ANTHROPIC_API_KEY
make eval                    # LLM-judged faithfulness
make serve                   # http://localhost:8000/docs  — answer questions
make ui                      # http://localhost:8501       — chat UI
```

Ask the API a question:

```bash
curl -s localhost:8000/ask -H 'content-type: application/json' \
  -d '{"question": "How long does the Atlas-7 battery last?"}' | jq
```

With Docker:

```bash
ANTHROPIC_API_KEY=sk-... docker compose up --build
```

## Layout

```
data/       sample document corpus (a fictional company knowledge base)

tests/      unit tests for chunking, store, and graph (no model download needed)
```

## Key decisions

- **In-memory NumPy store over a vector DB.** For a few thousand chunks, a
  normalised matrix with a dot-product search is faster to reason about and
  trivial to persist. The store interface is narrow on purpose — swapping in
  pgvector or Chroma later is a one-file change.
- **Local embeddings, hosted generation.** Embeddings run on
  `all-MiniLM-L6-v2` (free, no key); only the final generation call hits a paid
  API, which keeps cost-per-query low.
- **Graph expansion is opt-out, not always-on.** It helps multi-hop questions
  but adds lower-precision context; it's a toggle so its effect is measurable in
  the eval harness rather than a hidden default.
